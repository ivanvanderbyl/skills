# Optional web target

Read this when the user asks for a web surface that runs the same Swift core as the native apps. Web is optional: add it only on request, and declare it as a `web` target in the project state so its checks are tracked beside iOS and Android.

The route is the Swift core compiled to WebAssembly, with a typed TypeScript API generated by JavaScriptKit's BridgeJS plugin, rendered by the project's own web UI framework. BridgeJS is marked experimental by its authors. Record the choice as a decision, pin JavaScriptKit to an exact version, and prove one journey in a browser before porting further screens.

The facts below were observed with Swift 6.4.2, its matching `wasm` Swift SDK and JavaScriptKit 0.63.0, running the generated module in Node. Recheck them against the versions the project pins. A browser run, the embedded Swift SDK and `swift package js test` were not exercised.

## Keep the core free of the bridge

- Add a façade target, such as `AppWeb`, that depends on the core and on JavaScriptKit. It is the only target that imports JavaScriptKit or uses `@JS`. The core must keep building and testing on the host with `swift test`.
- The façade declares its own `@JS` types and maps them to and from core types, the same role the SwiftJava façade has on Android. Derive both façades from the same core types so an action added to the core fails to compile in each façade until it is mapped.
- The façade is an executable target with the `BridgeJS` plugin and the `Extern` experimental feature enabled. Its `main.swift` installs the event loop executor: `JavaScriptEventLoop.installGlobalExecutor()`.

## Build and consume

- Build with `swift package --swift-sdk <wasm-sdk-id> js --use-cdn`. Add `-c release` for a shippable module. Output goes to `.build/plugins/PackageToJS/outputs/Package/` unless `--output` is given.
- The typed surface is `bridge-js.d.ts`. `index.d.ts` declares only `init`.
- In Node: `const { exports } = await instantiate(await defaultNodeSetup())`, importing `instantiate` from `instantiate.js` and `defaultNodeSetup` from `platforms/node.js`. Run `npm install --ignore-scripts` in the output directory first; the Node setup needs `@bjorn3/browser_wasi_shim` even with `--use-cdn`.
- Run headless façade tests in Node before any browser journey. They are fast and catch mapping errors.

## How Swift types arrive in TypeScript

- `Int64` is `bigint`. Values above 2^53 round-trip. Callers write `7n`, and JSON encoding of a snapshot needs an explicit conversion.
- A `String` raw-value enum is a union of string literals.
- An enum with associated values is a discriminated union with labelled payload fields, such as `{ tag: Tag.Rename; recordID: string; title: string; expectedLocalRevision: bigint }`.
- A `@JS struct` is an interface and crosses by value.
- A `@JS protocol` is an interface that TypeScript implements. Use it for platform ports and observers. `async throws(JSException)` becomes a `Promise`.
- A `@JS class` has `new(...)` and `release()`. The web host must call `release()` when it discards a session.

## Rules that the generated glue enforces

- Put mapping initialisers for a `@JS struct` in an extension. A custom `init` in the struct body removes the memberwise initialiser that the generated glue calls, and the build fails.
- Dispatch synchronously. An `async` `@JS` method does not start in the caller's turn, so pending state is not visible when the call returns. Expose `send(action:)` that runs the core decision synchronously and returns a typed accepted or rejected result, publish later changes through a `@JS protocol` observer, and run effects in a `Task`.
- Do not mark a `@JS class` `@MainActor`; the generated glue fails with isolation conformance errors. Use `@JS final class …: @unchecked Sendable` and state the justification beside it: `wasm32-wasip1` is single-threaded and every job runs on the JavaScript event loop. Revisit this when threads are enabled.
- Catch a throwing TypeScript port in the façade and map it to the core's typed failure. Rejections cross as values, never as exceptions, and leave state unchanged.

## Platform adapters on the web

Persistence, network, credentials and scheduling stay host adapters, as on the native apps: implement the façade's port protocols in TypeScript over IndexedDB, `fetch` and the browser's storage and lifecycle events. Apply the same repository contract and sync policy as the native stores. A tab can be discarded at any time, so durable queued writes must be committed before the UI reports them saved.

## Size and build time

One small core with one feature measured about 4.0 MB in release with `wasm-opt` (1.4 MB gzipped) and 9.5 MB without it. A first release build took over five minutes on four cores; an incremental debug build took about ten seconds. Measure the project's own module, set a size budget with the user, and serve the module compressed. Install binaryen so the plugin can run `wasm-opt`.

## Shared journeys

Run the same journey files against the web target that run against iOS and Android. e2e documents a `web()` engine in `@e2e-dev/web` that sits in the same `targets` array as the mobile targets, with per-test `platforms` to scope a test. This was read from the documentation, not run; check the installed `e2e guide setup` before relying on it. Give web elements the same identifiers as the native targets, as `data-testid` or accessible names, and list them on the work item with `--ui-id`.

## What to verify before claiming the web target

- `web:unit`: the façade's Node tests pass against the release module.
- `web:journey`: the shared journey passes in a real browser against the built app.
- The core's host tests still pass and the native targets' checks are rerun, because the core's sources are inputs to every target.
